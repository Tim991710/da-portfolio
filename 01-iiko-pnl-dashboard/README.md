# План-факт P&L сети точек общепита

Учебный проект под вакансию «Аналитик данных» в сети street-food:
управленческая отчётность из сырых выгрузок, похожих на iiko, до модели
Power BI с план-факт анализом и разбором причин отклонений.

**Данные синтетические.** Сеть вымышленная, названия точек придуманы.
Структура и дефекты выгрузок воспроизведены по типовому OLAP-отчёту iiko и
соглашениям управленческой отчётности общепита, а не взяты из реальной системы.

## Задача

Собственник сети из 10 точек видит, что при росте выручки рентабельность
отдельных точек падает, но не понимает, где именно и почему. Отчётность
собирается вручную в Excel раз в месяц, цифры в ней не сходятся с кассой.

Нужно: единая витрина продаж, ФОТ и плана, отчёт с план-факт анализом и
разложением отклонения доли ФОТ на факторы, плюс журнал проверок, чтобы
расхождения ловились до того, как цифра уйдёт руководству.

## Стек

SQL (SQLite; порт под PostgreSQL — см. `sql/postgres_port.sql`), Power BI,
DAX, Power Query, Python + pandas (генерация и загрузка), Git.

- в актах списания 3 строки с отрицательным количеством (ошибка ввода);

## Как запустить

```powershell
python data_gen/generate_data.py   # синтетика -> data/raw
python sql/build_db.py             # landing -> витрины -> проверки -> data/marts
```

Затем собрать дашборд по `BUILD_GUIDE.md`. Проверка: сумма `revenue` в витрине
`dashboard_facts` должна совпасть с `mart_monthly_outlet` — в текущей версии
данных это 51,05 млн ₽.

## Модель

```
dim_date ──┬── fact_sales ── dim_dish
           │        │
           ├── fact_writeoff ── dim_dish
           │
           ├── fact_payroll
           │        │
           └── fact_plan
                    │
                 dim_outlet
```

`fact_payroll` и `fact_plan` связаны с `dim_date` по `month_start`
(первое число месяца), `fact_sales` — по `date_key`. Это ключевая деталь:
если связать ФОТ по дню, сумма умножится на число дней в месяце.

## Правила расчёта (зафиксированы в SQL и README)

1. **Выручка** = сумма `amount_paid` (после скидки), включая возвраты со знаком минус.
2. Дубли устраняются `DISTINCT` по всем полям строки.
3. Заказы со статусом `Deleted` в выручку не входят.
4. Строка с положительным количеством и отрицательной суммой после скидки
   считается ошибкой ввода и уходит в `quarantine_sales`, а не в выручку.
5. Код `D15N` сводится к `D15` (переименование блюда).
6. **ФОТ** = начисления (`accrual`). Если за месяц по точке выгрузки нет,
   показатель остаётся пустым, а не нулевым: иначе доля ФОТ занижается.
7. **Food cost %** = себестоимость / выручка.
8. **Маржинальность %** = (выручка − себестоимость) / выручка.
9. **Доля ФОТ %** = ФОТ / выручка.
10. **Операционная рентабельность %** = (выручка − себестоимость − ФОТ) / выручка.
    Аренда, коммунальные и маркетинг **не включены** — это не полный P&L.
11. **Отклонение доли ФОТ, п.п.** раскладывается на два фактора, которые
    в сумме дают ровно итог: эффект выручки и эффект ФОТ.
12. **Списания** = сумма `cost_sum` по актам. Строки с отрицательным количеством
    считаются ошибкой ввода и в витрину не попадают.
13. **Рентабельность со списаниями** = (выручка − себестоимость − ФОТ − списания) / выручка.
    Основной показатель в отчёте считается без списаний — они вынесены отдельным
    блоком, чтобы не менять методику задним числом.

## Результаты по сети за 24 месяца

| Показатель | Значение |
|---|---|
| Выручка | 51,05 млн ₽ |
| Food cost | 42,5 % |
| Доля ФОТ | 24,1 % |
| Операционная рентабельность (без списаний) | 33,4 % |
| Операционная рентабельность (со списаниями) | 32,4 % |
| Списания | 558 289 ₽ — 1,1 % выручки, 2,6 % food cost |
| Средний чек | 341–456 ₽ |

Списания по причинам: брак, порча, истечение срока, дегустация, ошибка кассира.
В отчёте они показаны отдельным блоком: это деньги, которые уже потрачены на
закупку, но не принесли выручки.

## Что показал анализ

1. **Сеть в целом держит долю ФОТ.** 23,8 % в ноябре 2024 против 23,1 % в
   октябре 2026 — колебания в пределах 1–2 п.п., тренда на разбалансировку нет.
   Проблема локальная, и общий отчёт её маскирует.
2. **Два проблемных случая.** T03 (падение трафика с марта 2026) держит долю
   ФОТ 27,3 % против 23,9 % по сети. T07 (открыта в феврале 2026) — 26,9 %,
   что нормально для выхода на плановый объём, но требует отдельного плана ФОТ
   на ramp-up.
3. **В T03 отклонение создано не ставками.** Сентябрь 2026: план 21,0 %,
   факт 35,2 %, отклонение +14,2 п.п. Из них +1,2 п.п. дала просадка выручки и
   +13,0 п.п. — превышение ФОТ над планом. Причина видна в данных: план ФОТ
   считался как 21 % от плановой выручки, а график смен при падении трафика не
   пересматривался. Первый шаг — согласовать с операционным отделом пересмотр
   нормативов смен на точке, а не искать экономию в ставках.
4. **Расхождения в выгрузке реальны, но объяснимы.** Все 15 проверок проходят;
   единственный `WARN` — отсутствие ФОТ за март 2026 по T05, показатель оставлен
   пустым и вынесен на сверку с бухгалтерией, а не заменён нулём.
5. **Списания забирают 2,6 % food cost.** 558 289 ₽ за 24 месяца — больше, чем
   экономия от пересмотра ставок. Половина приходится на брак и порчу, то есть
   на процессы, а не на закупочные цены. Это первый кандидат на разбор с
   операционным отделом после ФОТ.

## Ограничения

- Данные синтетические: цифры показывают методику, а не состояние реальной сети.
- Объём урезан (10 точек вместо 50+) ради размера репозитория.
- Операционная рентабельность не включает аренду, коммунальные, маркетинг и
  амортизацию, поэтому она выше бухгалтерской.
- SQLite вместо PostgreSQL; порт запросов лежит рядом, но не прогонялся на сервере.
- Нет интеграции по API: это отдельный проект.
- Скриншот и PDF дашборда собраны на предыдущей версии генератора (выручка
  51,42 млн). Текущая версия с расширенной выгрузкой даёт 51,05 млн — чтобы
  картинка совпала с цифрами, отчёт нужно обновить в Power BI (`Обновить`).
- Канал продажи и тип оплаты есть в данных, но в дашборд ещё не выведены:
  в отчёте остались только P&L-показатели.
